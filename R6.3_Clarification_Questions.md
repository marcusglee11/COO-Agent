**Impact**: Documentation clarity for future maintainers.

### Q2: VerificationResult Type Definition (Section A4)

**Reference**: Section A4 specifies `verify_amu0_complete(amu0_path) -> VerificationResult` but does not define the VerificationResult type.

**Question**: What should the VerificationResult type contain?

**Options for Consideration**:
1. **Boolean + Exceptions**: Return True or raise GovernanceError (fail-fast)
2. **Typed Object**: Return structured result with:
   ```python
   class VerificationResult:
       is_valid: bool
       errors: List[str]
       warnings: List[str]
       verified_hash: bytes
       verified_signature: bool
   ```
3. **Enum-based**: Success/Warning/Failure with associated messages

**Impact**: Determines error handling patterns across entire codebase.

**Recommendation**: Option 1 (Boolean + Exceptions) aligns with fail-closed philosophy, but Option 2 provides better debugging information.

### Q3: CPU Microcode Capture Specification (Section B1)

**Reference**: Section B1 requires "cpu_microcode MUST be captured using /proc/cpuinfo (or equivalent deterministic Linux path)".

**Question**: Which field from /proc/cpuinfo should be used, given vendor differences?

**Context**:
- Intel CPUs: `microcode` field (e.g., "0x2f")
- AMD CPUs: `microcode` field exists but format differs
- Some systems: Field may be empty or require root permissions

**Options for Consideration**:
1. Capture `microcode` field exactly as-is (vendor-agnostic)
2. Define vendor-specific parsing rules
3. Capture entire CPU info block and hash it
4. Fail if microcode field is empty/unavailable

**Impact**: Platform compatibility and determinism guarantees.

**Recommendation**: Option 1 with Option 4 as fallback (fail-closed if unavailable).

### Q4: Runtime Initialization Sequence (Section B3)

**Reference**: Section B3 states "All deterministic operations MUST be preceded by this call" for `initialize_runtime(amu0_path)`.

**Question**: What is the exact initialization sequence, particularly:
1. When should `initialize_runtime()` be called relative to FSM initialization?
2. Should Gates call it, or assume it's already called?
3. What about test harnesses - should they call it in `setUp()`?
4. If called multiple times, should it error or be idempotent?

**Impact**: Every script entry point (freeze, gates, replay, rollback, migration).

**Suggested Specification**:
```
initialize_runtime() MUST be called:
- ONCE per process lifetime
- BEFORE any FSM instantiation
- BEFORE any Gate execution
- BY the top-level script (freeze.py, run_gates.py, etc.)
- Multiple calls should raise GovernanceError
```

### Q5: Time Pinning Verification Threshold (Section B4)

**Reference**: Section B4 states "Difference > 1s MUST raise GovernanceError".

**Question**: Should the 1-second threshold account for:
1. Subprocess startup overhead (typically 10-100ms)?
2. System clock resolution/granularity?
3. Is this an absolute difference or should it use a confidence interval?

**Context**: On some systems, subprocess spawn + time.time() call may introduce 50-200ms of variance even with perfect time pinning.

**Options for Consideration**:
1. **Strict 1s absolute**: Any difference > 1.0s fails
2. **Startup-adjusted**: Threshold of 1.0s + 100ms grace period
3. **Configurable**: Read threshold from pinned_context.json

**Impact**: False positives on slower systems or high-load environments.

**Recommendation**: Option 2 (1.1s threshold) with clear documentation of the grace period rationale.

### Q6: Pinned PATH Derivation (Section E2)

**Reference**: Section E2 states "`run_pinned_subprocess` MUST override PATH to a pinned, deterministic set of directories derived from AMU₀ context."

**Question**: How should the pinned PATH be derived/stored?

**Options for Consideration**:
1. **Hard-coded in code**: PATH="/usr/bin:/bin" (simplest, least flexible)
2. **New manifest field**: Add `pinned_path` to environment_manifest.json
3. **Derived from tools_manifest.json**: Extract paths from tool locations
4. **Captured during AMU₀ creation**: Store current PATH in pinned_context.json

**Impact**: Tool availability, determinism, and AMU₀ portability.

**Recommendation**: Option 2 (manifest field) for explicit control, or Option 1 for maximum determinism.

**Follow-up**: Should PATH be verified against a whitelist? Should it fail if a required tool is not in PATH?

### Q8: Breaking Changes and Migration (General)

**Reference**: Sections A3, A5 introduce breaking changes to AMU₀ structure and canonical hash calculation.

**Question**: What is the migration strategy for existing AMU₀s created under R6.2?

**Options for Consideration**:
1. **Clean break**: R6.3 cannot use R6.2 AMU₀s, require fresh capture
2. **Migration tool**: Provide script to convert R6.2 → R6.3 AMU₀ format
3. **Version field**: Add `amu0_version` to tracker, support both formats
4. **Deprecation period**: R6.3 supports R6.2 format with warnings, R6.4 removes support

**Impact**: Development continuity, testing, rollback compatibility.

**Recommendation**: Option 1 (clean break) for R6.3 with clear documentation that R6.2 AMU₀s are incompatible.

### Q9: Windows Development Environment (Section B2)

**Reference**: Section B2 mandates "If sys.platform != 'linux', raise ImportError" at earliest import point.

**Question**: How should development/testing proceed on non-Linux systems?

**Context**: Current development has occurred on Windows. R6.2 tests pass on Windows with platform checks.

**Options for Consideration**:
1. **Strict enforcement**: All development must move to Linux immediately
2. **Dev mode flag**: Allow `COO_DEV_MODE=1` to bypass platform check (with warnings)
3. **Test-only bypass**: Platform check disabled in test harnesses only
4. **Conditional import**: Separate `coo_runtime_dev` package for non-Linux

**Impact**: Development velocity, CI/CD setup, developer workflow.

**Recommendation**: Seek explicit guidance. If strict Linux-only is required, recommend Option 1 with transition timeline.

### Q10: Unified Signature Protocol Interface (Section D2)

**Reference**: Section D2 specifies a Signature class with four methods but no parameter signatures.

**Question**: What are the exact method signatures?

**Suggested Specification**:
```python
class Signature:
    def sign_data(data: bytes, private_key_path: str) -> bytes:
        """Sign arbitrary bytes"""
    
    def verify_data(data: bytes, signature: bytes, public_key_path: str) -> bool:
        """Verify signature over bytes"""
    
    def sign_file(filepath: str, private_key_path: str) -> bytes:
        """Read file and sign contents"""
    
    def verify_file(filepath: str, signature: bytes, public_key_path: str) -> bool:
        """Read file and verify signature"""
```

**Alternative**: Should these be instance methods or class methods/standalone functions?

**Impact**: API usability and consistency across all signature operations.

**Recommendation**: Confirm interface or approve suggested specification above.
